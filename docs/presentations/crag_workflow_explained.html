🌐 Architectural Overview
StateGraph Engine

The Second Brain system executes a deterministic 7-node LangGraph Corrective RAG (CRAG) workflow backed by AsyncSqliteSaver checkpointing. It prevents hallucination by enforcing epistemic boundaries and factual grading barriers.

  • Start ➔ Node 1 (rewrite_query): Anaphora resolution, domain lexicon scanning, polysemy collision alerts, and intent pre-scoring.
  • Conditional Edge 1: needs_retrieval=False ➔ Node 2 (direct_reply) ➔ END. Otherwise ➔ Node 3 (retrieve).
  • Node 3 (retrieve) ➔ Node 4 (rerank): Federated hybrid vector search across isolated domains fused via calibrated RRF, then re-scored by FlashRank cross-encoder.
  • Node 5 (grade_context): Fast score pre-filter followed by a single batched structured LLM call validating factual relevance.
  • Conditional Edge 2: len(graded_chunks) > 0 ➔ Node 6 (synthesize). If 0 chunks survive ➔ Node 7 (fallback_notice).

🔍 Node 1: `rewrite_query` Operational Anatomy
Input Processor & Router

Node 1 is the gatekeeper of the RAG pipeline. Before calling any LLM, it queries relational taxonomy tables in SQLite and runs a fast lightweight intent classifier.

1. Domain Lexicon & Polysemy Scan

Queries domain_lexicon to find homonyms (e.g. "margin" in finance vs "margin" in engineering; "depreciation"; "ESD"). When a term belongs to $\ge 2$ domains, builds a contrastive_warning injected into the LLM prompt.

2. Cross-Domain Entity Linking

Queries cross_domain_entities table for canonical equipment or asset tags (e.g., "Power Transformer T-101"). Injects matched entity names into the prompt and carries them to retrieval for rank boosts.

3. Laya Classifier Pre-Score

Runs LayaDomainClassifier (target <20ms) over the query. Returns primary_domain and confidence. Provides an objective empirical prior to guide the LLM's query decomposition.

Node 1 Activation Modes: When & Under What Conditions?

Mode 1A: Direct Reply
_GREETING_RE.match(query) OR needs_retrieval == False

Trigger: User submits conversational pleasantries ("hello", "who are you", "thanks") or purely assistant-meta queries.
Routing: Routes to Node 2 (direct_reply), bypassing all vector searches.

Mode 1B: Single Domain
len(target_domains) == 1 AND polysemy == 0

Trigger: Clear single-domain intent (e.g. "how to write python code" ➔ general). No polysemic collisions detected.
Routing: routing_mode="single", generates 1 tailored sub-query with weight 1.0.

Mode 1C: Multi-Domain Federated
polysemy > 0 OR len(target_domains) >= 2

Trigger: Cross-cutting query across engineering, economics, or law (e.g. "Transformer T-101 maintenance cost and legal compliance").
Routing: routing_mode="multi", decomposes into distinct sub-queries per domain.

Mode 1D: Explicit Operator Lock
domain_filter.mode == "explicit"

Trigger: User explicitly clicks UI domain toggle pills (e.g. [Eng] or [Law]).
Routing: Overrides classifier pre-scoring. Restricts target_domains and sub-queries strictly to user-selected domains.

⚡ Node 3: Hybrid Federated Retrieval & RRF Fusion
Vector Retrieval Engine

Node 3 executes parallel hybrid searches across partitioned domains in Qdrant (dense BAAI/bge-m3 + sparse BM25/BgeM3Sparse) and unifies candidates using Domain-Calibrated Reciprocal Rank Fusion.

$$\text{RRF Score}(c) = \sum_{d \in D} \frac{\text{DomainWeight}_d}{60 + \text{Rank}_{d, c}} + \mathbb{I}_{\text{EntityMatch}}(c) \cdot \frac{1}{60}$$

Node 3 Activation Modes: When & Under What Conditions?

Mode 3A: Auto Federated Scatter-Gather
domain_filter.mode != "explicit" (mode == "auto" or empty)
  • Automatic General Fallback: If the user did not specify explicit domains, the retriever automatically injects a "general" partition sub-query.
  • 0.5x RRF Discount: Chunks from the general domain have their domain weight scaled down by 0.5x, ensuring specialized domain chunks take precedence unless no specialized knowledge exists.
  • Parallel Qdrant Queries: Executes simultaneous asyncio.gather searches per domain partition.
  • Stratified Per-Domain Quota: Guarantees min_per_domain = 2 chunks from each active domain to prevent single-domain starvation.
Mode 3B: Explicit Partition Lock
domain_filter.mode == "explicit"
  • Strict Partition Isolation: Restricts vector queries strictly to the domains selected by the operator (e.g. only engineering).
  • Zero General Fallback: Explicitly removes the "general" domain query unless the user specifically clicked the [Gen] pill.
  • Strict Payload Filtering: Enforces Qdrant filters: must: [domain IN user_domains], authority_tier <= max_tier, is_current == True.
  • Entity Boost: Any chunk mentioning the recognized cross-domain entity receives an immediate $+ \frac{1}{60}$ bonus.
🎯 Node 5: `grade_context` Mechanism & Validation
Corrective Quality Gate

Node 5 prevents hallucinations and off-topic synthesis. It acts as an adversarial filter to verify whether retrieved passages actually answer the user's inquiry.

1. FlashRank Score Pre-Filter

Immediately drops any chunk where rerank_score < score_threshold (default 0.0). Eliminates mathematically dead candidates before calling the LLM.

2. Prompt Injection Neutralization

Sanitizes untrusted text via _XML_TAG_RE.sub("[document-tag]", text) to prevent adversarial prompt injection through PDF or web uploads.

3. 1-Batched Structured LLM Call

Packages remaining chunks into <documents><document index="1">...</documents> and invokes BatchGradeResult. Returns relevant_indices: [1, 2, ...].

⚖️ Validation Criteria & Branching Logic
Conditional Edge 2

What Exactly Is Validated?

  • Direct Factual Utility: Does the passage contain direct evidence that answers the specific user query?
  • Irrelevant Context Rejection: Even if a chunk matches keywords (e.g. has the word "Python" in a complex machine learning math chapter), if it does not answer "how to improve python skills", it is marked irrelevant ([]).
  • Domain Fidelity: Verifies that engineering claims are not answered with purely legal disclaimers.

Post-Grading Routing

len(graded_chunks) > 0 ➔ Node 6 (synthesize)
len(graded_chunks) == 0 ➔ Node 7 (fallback_notice)

If zero chunks survive grading, the system refuses to speculate, immediately invoking fallback_notice to protect user trust.

✍️ Node 6: `synthesize` & Epistemic Boundaries
Evidence-Grounded Generator

Node 6 synthesizes answers using strictly validated evidence. Every claim must carry a verified citation marker ([1], [2]), and out-of-range citations are automatically stripped.

Node 6 Activation Modes: When & Under What Conditions?

Mode 6A: Standard Grounded Synthesis
len(specialized_domains) < 2

Trigger: The surviving graded chunks belong to either 0 or 1 specialized domain (e.g., only general or only engineering).

  • Uses _SYNTHESIZE_SYSTEM_PROMPT.
  • Produces a clean, unified Markdown explanation with inline numeric citations ([1], [2]).
  • Fast generation without cross-domain overhead.
Mode 6B: Multi-Domain Epistemic Synthesis
len(specialized_domains) >= 2

Trigger: Graded chunks span $\ge 2$ specialized epistemic domains (e.g. engineering AND economics AND/OR law).

  • Mandatory 4-Part Structure:
    1. ⚙️ Engineering Perspective (Physical limits, technical standards)
    2. 📈 Economic Perspective (Valuation, cash flow, depreciation)
    3. ⚖️ Legal Perspective (Statutes, liabilities, compliance mandates)
    4. 🔀 Inter-Domain Conflict & Priority Matrix (Tradeoff synthesis)
  • Language Adaptation: Automatically renders headings in Vietnamese or English based on query language.
